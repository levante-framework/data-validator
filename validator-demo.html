1. Trigger and validate the request

Cloud Scheduler calls the Cloud Run Job API directly. Postman, curl, and the CLI use the thin HTTP trigger or the same Run Job API. Pydantic rejects malformed data-validation payloads before the pipeline starts.

What “validated” means

Keep useful data; make quality visible

The app distinguishes records it cannot parse from records that parse but fail a research rule.

01 Schema failure

Missing required fields, incompatible types, or invalid object structure. The row is excluded from its main table and recorded in invalid_data with the error.

02 Soft validation failure

The row is structurally usable, so it remains in the main table with valid_*=false and a specific validation_msg_*.

03 Warning

Non-blocking concerns—such as some trial-index issues—are retained in warning fields without automatically invalidating the record.

A User rules

  • Required IDs and user type
  • Student birth month/year and age checks
  • Scope, activity window, and relationship inclusion

B Run and trial rules

  • Required run/task/variant relationships
  • Completion, practice/test trial, timing, and response checks
  • Run validity informed by its associated trials

C Survey rules

  • Survey schema and response parsing
  • Completion and relationship checks
  • Student, teacher, and caregiver counts

Safety and recovery

Do not turn partial success into a release

Failure behavior is part of the product: downstream publication is gated, errors are visible, and recoverable work is retried.

No data change

quiet success

Skip raw upload and notebook work. If there is no pending processed next, finish without a release notification.

GCS upload failure

blocked

Do not import or release Redivis. This prevents stale GCS tables from becoming a new raw version.

Notebook failure

exit 1

Do not release processed. The per-site Slack summary names the failing processed step; Cloud Scheduler can retry.

Processed release failure

recoverable

Return a failure instead of a false success. A later unchanged-GCS run can publish the pending next without rerunning the notebook.

Old notebook job visible

rejected

Require a new currentJob.id after run(); never adopt the previous site's lastRunJob as this run.

Shared notebook busy

wait / retry

Wait for the current shared workflow to become idle, then re-point its site datasource immediately before starting.

            data_validation
            
Per-site or multi-org pipeline

            
Extract, validate, publish raw, process, release, and report. This is the default when operation is omitted.

          

          

            special_dataset_validation
            
Airtable-defined combined dataset

            
Build several organization scopes into one raw/processed pair, with a safe TEST-* redirection mode.

          

          

            redivis_individual_release
            
Provision individual sites

            
Coordinate Airtable metadata, Redivis dataset shells/status, and daily Scheduler jobs; optionally target one site.

          

          

            open_assignments_sync
            
Sync open assignments

            
Read current Airtable/Firestore state and synchronize assignment metadata, with a non-writing dry-run option.

          

          

            weekly_report
            
Summarize operational health

            
Report site activity, Redivis state, validation health, schema drift, Scheduler health, and caught crashes.

          

          

            migrate_scheduler_jobs
            
Move legacy Scheduler targets

            
One-time helper to identify or retarget older jobs to the Cloud Run Job API; supports dry-run.
